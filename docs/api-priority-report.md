> 대상: 세일즈맵 API·백엔드 팀 / 목적: MCP(AI 연동) 관점의 API 개선 필요를 **우선순위(별점) + 실사용 근거**로 보고
> 구조: [원장 salesmap-api-issues.md](salesmap-api-issues.md)와 **같은 번호·같은 순서**. 원장의 기술 상세를 담고 그 위에 로그·VOC·레퍼런스로 보강한 확장본 (원장보다 얇으면 안 됨)
> 근거 데이터: MCP 텔레메트리 (베타 워크스페이스 ~77개, 2026-06-01~07-23, 24K+ 호출)
> 최신화: 2026-07-23 / 별점: 초안(AI) — 담당자가 항목별로 직접 확정

## 우선순위 표기 (제목 앞 별점)

| 별점 | 의미 |
|---|---|
| **★★★** | 원천 불가 — API로 아예 안 됨. 로그에서 플로우 끊김 다수 또는 고객 직접 VOC |
| **★★** | 심각한 비효율 — 가능은 하나 심각한 타격 (배치 없어 느리지만 되긴 함 등) |
| **★** | 우회+소폭 비효율 — MCP로 우회하되 내부 비용(스키마 조회·왕복 등) 발생 |
| **(없음)** | 참고용 — 우회되고 성능 문제도 없음. 뉴버전 설계 시 참고 |

## 1. ★★★ Batch Create / Update API 부재

**문제** — 생성(`POST /v2/{type}`)·수정(`POST /v2/{type}/{id}`)이 1건씩만 가능. 다건 처리 엔드포인트가 없음. (조회는 `POST /v3/object/read`로 500건 배치 해결됨)

**실제 영향** — "이 리드 20건 담당자 바꿔줘" = 20번의 개별 POST. AI는 툴콜을 N번 반복하고, 각 응답이 컨텍스트에 쌓여 토큰을 낭비하며, 사용자는 분 단위 대기. 클라이언트 스로틀(120ms)로 순차 직렬화되어 벽시계가 선형 증가.

**로그/VOC** — create/update 전체 2,049콜 분석 (6/1~7/23):
- **86%(1,759콜)가 "5건 이상 연속 버스트"** 안에서 발생 — 실제 용도가 사실상 배치
- 최악: 고객 **598명에 불리언 1개** 켜기 = **598콜 연속, 19.8분** (Fast campus, 6/12). 3일 뒤 225건 재분류 반복
- 반복 업무: 한 계정 **7월에만 버스트 12회** (교육 프로그램 선발/참여 — 매주 도는 정기 업무)
- 임포트: 회사 37건 연속 생성 4.6분, 실패 3건 (SK렌터카)
- 버스트 동안 우리 스로틀이 워크스페이스 rate limit의 **~83% 지속 점유** → 동료 AI 사용까지 밀림

**레퍼런스 — HubSpot**: create·update 최대 100건. create는 body에 `associations` 배열 동봉해 "생성하며 연결" 가능.
```
POST /crm/v3/objects/deals/batch/create
  { inputs: [{ properties: {...}, associations: [{ to:{id}, types:[...] }] }, ...] }
POST /crm/v3/objects/deals/batch/update
  { inputs: [{ id, properties: {...} }, ...] }
```
세일즈맵은 연결이 관계 필드라 batch update가 관계 필드를 수용하면 HubSpot의 batch association까지 커버(#20).

**현재 우회와 비용** — 단건 반복 또는 run-script 순회(120초 상한 + 가드레일로 쓰기엔 소극적). 근본 해결 아님.

**API 개선안** — `POST /v3/object/create`·`update` 다건 입력(최대 100건), create는 association 동시 세팅. v3 create가 전 오브젝트 지원되면 `salesmap-batch-create-objects` 도구로 노출. → batch 100 기준 **1,759콜 → 63콜(28배), 121분 → 1~2분**.

## 2. ★ fieldList 타입 키 패턴

**문제** — 필드 값을 쓸 때 타입별로 다른 값 키(`stringValue`/`numberValue`/`userValueId`…)를 15개+ 알아야 함.

**실제 영향**:
```json
// 세일즈맵: 타입마다 다른 값 키
{ "fieldList": [
    { "name": "담당자", "userValueId": "uuid" },
    { "name": "금액",   "numberValue": 50000 },
    { "name": "참여자", "userValueIdList": ["uuid1","uuid2"] }
]}
```
LLM이 타입을 모르면 잘못된 키를 씀. 실사용 실패: `{ "부가 서비스": "A" }` 요청 — 복수선택 필드라 `{ "name":"부가 서비스", "stringValueList":["A"] }`여야 하는데 AI가 단일 문자열로 보내 `"부가 서비스에 stringValueList가 없습니다"` 거부.

**레퍼런스 — HubSpot** (2026-07 공식 재검증): 평탄 name→value, 타입 키 없음. 타입별 부담이 "값 표기 규칙"(날짜=ISO/epoch, 복수선택=세미콜론)으로만 남고 그마저 관대 — **복수선택에 단일 문자열 보내도 400 아니라 수용**. LLM이 타입 몰라도 대부분 통과. **API 주 소비자가 AI가 된 시대엔 서버가 흡수하는 게 맞는 설계.**

**현재 우회와 비용** — `resolveProperties()`가 매번 `/v2/field/{type}` 스키마 조회 후 타입별 키로 변환. AI가 자연값만 넘기게 흡수하지만 **매 쓰기마다 스키마 조회 1회 추가**, MCP 거칠 때만 흡수(직접 API·공식 MCP엔 그대로 노출).

**API 개선안** — 이름-값만 받고 서버가 스키마로 타입 해석 (#3 위치 통일과 한 묶음, 뉴버전 기본 원칙).

## 3. ★★ Top-level 파라미터 분리 (위치 이중성)

**문제** — 같은 "필드 값 쓰기"인데 값 넣는 **위치가 3갈래**. AI가 매 필드마다 판단해야 함.

**실제 영향**:
```
POST /v2/deal
{
  "name","price","pipelineId","pipelineStageId","status",  ← ① top-level 전용 필드
  "peopleId","organizationId",                             ← ② top-level primary 관계
  "fieldList": [ { "name":"담당자","userValueId":"uuid" } ]  ← ③ fieldlist 나머지 필드 + fieldlist custom 관계
}
```
세 종류 실패 실제 발생:
1. **유지보수 번거로움** — MCP 레이어에서 우회는 가능하나 하드코딩 방식이라 유지 취약
2. **silent no-op (가장 위험)** — 잘못된 위치·키로 보내면 API가 거부 없이 `200 OK` + 값만 조용히 버림(`updatedAt`만 갱신). 관찰된 케이스: top-level `ownerId`(담당자)·고객 `email`/`phone`·스키마 없는 임의 파라미터(`foobar`) 전부 미반영. → AI가 "완료"로 오판, 사용자에게 틀린 보고. 재조회 안 하면 아무도 모름. 400 거부보다 나쁜 조용한 데이터 유실

**레퍼런스** — Salesforce: 기본 연결도 전부 필드. HubSpot: 전부 association 리소스. 어느 쪽이든 "같은 개념은 같은 문법". 세일즈맵만 혼합.

**현재 우회와 비용** — `TOP_LEVEL_ONLY` 맵으로 값을 top-level 추출. 단 예외 하드코딩 유지 취약 / 파이프라인 이름→ID 커버 실패 / 기본 연결(회사·고객)은 미적용(AI가 여전히 top-level id 사용) / `resolveProperties()` 복잡. (부분 개선: 맵에 `"회사"→organizationId`·`"고객"→peopleId` objectType-스코프 추가 시 흡수 — 코드 십수 줄)

**API 개선안** — top-level·기본연결·커스텀연결을 전부 fieldList로 통일 + 서버 타입 해석(#2와 한 묶음). ※breaking change라 뉴버전에서만.

## 4. Search API 제한

### 4-1. ★★ 정렬 미지원

**문제** — `sorts` 파라미터를 보내도 API가 무시. 금액순·최신순 정렬이 서버단에서 불가.

**현재 우회와 비용** — 전체를 가져와 클라이언트에서 정렬해야 하나 페이지네이션과 충돌(1페이지 50건만 정렬됨). 사실상 완전 우회 불가.

**API 개선안** — search `sorts` 실제 작동.

### 4-2. ★ 빈 필터 불가

**문제** — `filterGroupList: []`를 보내면 에러. 전체 목록 조회가 search로 안 됨.

**현재 우회와 비용** — `{ fieldName:"이름", operator:"EXISTS" }` 더미 필터 삽입. 비용은 작음.

**API 개선안** — 빈 필터를 전체 조회로 허용.

### 4-3. ★ 응답이 `{id, name}`만 반환

**문제** — search 결과가 id·name만. 상세 필드는 batch-read를 이어서 호출해야 함.

**실제 영향** — search→batch-read **2단 호출(N+1)** 강제.

**레퍼런스 — HubSpot**: search 요청에 `properties:[...]` 주면 결과에 해당 필드 포함.

**현재 우회와 비용** — MCP가 batch-read를 별도 호출로 이어붙임 (왕복 1회 추가).

**API 개선안** — search에 `properties[]` 지원.

### 4-4. ★★★ custom-object 검색 미지원

**문제** — search가 people·organization·deal·lead 4종만. 커스텀 오브젝트 조건 검색 불가.

**실제 영향** — 커오 레코드는 전량 조회 후 클라이언트 필터뿐. 티켓처럼 커오를 메인 워크플로우로 쓰는 팀은 "이번 주 VOC 티켓"조차 서버 검색 불가. **AI 입장에서 특히 큰 짐** — 조건 하나로 끝날 조회를 전량 로드→코드 필터로 우회해야 하니 run-script를 강제당하고, 데이터가 커지면 그마저 120초 상한·컨텍스트 한계에 막혀 사실상 불가.

**로그/VOC** — 커오 활용 팀이 run-script `getAll` 전량 스캔으로 우회 (티켓·Meissa 세션).

**레퍼런스 — HubSpot**: 커오도 표준과 동일한 `/crm/v3/objects/{type}/search`. 구분 없음.

**현재 우회와 비용** — 전량 스캔. 수백 건이면 낭비, 수천 건이면 사실상 불가 — 우회가 데이터 규모에 따라 원천 붕괴.

**API 개선안** — search의 커스텀 오브젝트 지원.

## 5. ★ Association 구조 차이 (engagement association 없음)

**문제** — association API가 `primary`/`custom`으로 분리돼 있고, **활동(engagement)에 대한 association이 없음**. "이 고객의 메모/이메일"을 관계로 못 당김.

**레퍼런스 — HubSpot**: engagement도 association 대상. `list-associations(contact, notes)` → note id → batch-read.

**현재 우회와 비용** — activity API(`list-engagements`)를 별도로 래핑해 우회. 관계 조회와 활동 조회가 이원화됨.

**API 개선안** — engagement를 association 대상에 포함 (원장 #14 아키텍처 방향과 연결).

## 6. ★ Rate Limit 미문서화

**문제** — 10초당 100건 제한(추정), 초과 시 429. 공식 문서화 안 됨.

**실제 영향** — AI는 병렬·고속 호출 패턴이 일반적이라 batch-read·association 카운트·engagement 조회가 겹치면 쉽게 한도 도달.

**현재 우회와 비용** — 모든 호출 전 120ms 인터벌 강제 + 429 시 body의 "N초 후" 파싱 백오프. 응답 시간이 불필요하게 늘어남. (워크스페이스 통합 버킷이라 동료 사용까지 영향 — #1 참조)

**API 개선안** — rate limit 공식 문서화 + 읽기/쓰기 분리·유저 라이선스 연동 스케일링 검토(경쟁사 비교: Attio 읽기 100/초, HubSpot 190/10초, 세일즈맵 100/10초로 최하위).

## 7. (참고) 응답 래핑 비일관성 — 기본 오브젝트는 배열, 커오·노트는 객체

**문제** — 단건 조회에서 레코드를 감싸는 형태가 갈림. **기본 오브젝트 4종은 1요소 배열, 커스텀 오브젝트·노트는 객체.**

**실제 영향** — 실측(2026-07): `deal`·`organization`·`people`·`lead` 전부 `data.{type} = 배열[1]`로 **일관**(1건인데 배열로 감싸는 점만 어색). `custom-object`·`memo`는 `data.{type} = 객체`. 즉 "타입마다 제각각"이 아니라 두 갈래. 기본 오브젝트가 오히려 배열이고 커오가 객체인 건 **설계 세대 차이 추정** — 기본 오브젝트는 초창기라 목록의 `dealList:[...]` 배열 관습을 단건에도 적용, 커오·노트는 나중에 "1건이면 객체로" 상식적으로 구현.

**현재 우회와 비용** — `getOne()`이 타입을 안 따지고 "온 값이 배열이냐"만 보는 범용 로직으로 흡수: 배열이면 `[0]`, 아니면 그대로. 딜이든 커오든 호출부는 객체 하나를 받음. 성능·기능 영향 없음.

**API 개선안** — 뉴버전에서 단건 조회를 1요소 배열이 아닌 객체로 통일. 우선순위 최하 — MCP 범용 로직으로 이미 완전 흡수.

## 8. ★★★ 누락된 API (TODO 생성 · 이메일 템플릿 생성 · 시퀀스 생성 · 시퀀스 등록)

**문제** — CRM 일상 업무의 쓰기 작업 여럿이 API에 없거나 500을 반환:

| 기능 | 현재 상태 |
|---|---|
| TODO 생성 | `POST /v2/todo` → 500 |
| 이메일 템플릿 생성 | API 없음 |
| 시퀀스 생성 | API 없음 |
| 시퀀스 등록 | `POST /v2/sequence/enrollment` → 500 |

**실제 영향** — "팔로업 TODO 만들어줘" 불가는 물론, **아웃바운드 자동화 플로우가 통째로 막힘**:
```
이메일 템플릿 생성 → 시퀀스 생성 (템플릿 조합) → 시퀀스 등록 (리드 배정)
     API 없음            API 없음                 500
```
"이 리드 20명에게 온보딩 시퀀스 돌려줘"는 등록만 있으면 되지만, **"이런 내용으로 3단계 팔로업 시퀀스 만들어서 돌려줘"(AI에게 가장 자연스러운 요청)는 템플릿부터 등록까지 전부 필요** — 셋 다 없어서 아웃바운드 자동화 전체가 GUI 전용. AI가 이메일 문구를 제일 잘 쓰는데 정작 그걸 시퀀스로 만들 방법이 없는 아이러니.

**레퍼런스 — HubSpot**: 시퀀스 등록 API(`/automation/v4/sequences/enrollments`) + 이메일 템플릿 CRUD(`/marketing/v3/transactional`·templates API) 제공.

**현재 우회와 비용** — 없음. 우회 불가.

**API 개선안** — 플로우 순서대로: ① 이메일 템플릿 생성 ② 시퀀스 생성(템플릿·대기일 스텝 구성) ③ 시퀀스 등록(enrollment 500 수정). 셋이 갖춰져야 "AI가 캠페인을 설계하고 돌리는" 시나리오가 열림.

## 26. ★ 관계 필드 검색 — LIST_CONTAIN 미지원 + 힌트 오발동

**실제 영향** — "참여자(다중)에 특정인 포함" 검색 시 LLM이 자연스러운 `LIST_CONTAIN` 선택 → 거부. 정상 UUID여도 실패. 과거 MCP 힌트가 "UUID 확인하라"로 오발동해 무한 삽질(고객 사례: 5회 연속 실패).

**현재 우회와 비용** — MCP가 관계 필드의 `LIST_CONTAIN`→`IN` 자동 remap + 힌트 분기 수정 완료. 사실상 해소됨(백엔드가 CONTAINS 받으면 remap 제거 가능).

**API 개선안** — 관계 필드에 LIST_CONTAIN 지원(또는 미지원 시 명확한 IN 권장 메시지).

## 27. (참고) 페이지네이션 — nextCursor를 받고도 LLM이 추가 탐색 안 함

**문제** — 커서 페이지네이션 자체는 정상. 문제는 소비자(LLM)가 `nextCursor`를 받고도 "이게 전부"로 단정하고 멈추는 것. 응답에 "일부다, 이어서 조회하라" 신호가 없음.

**실제 영향** — "전체 활동 요약해줘" → 최근 50건만 보고 결론 → 불완전 분석. 전체 건수 미제공이라 "50/50"인지 "50/230"인지 구분 불가.

**현재 우회와 비용** — `ok()`에서 nextCursor 존재 시 "더 있음 + `after=`" 힌트 자동 주입으로 해소.

**API 개선안** — 응답에 `total`(또는 `hasMore`) 포함 + activity 정렬·size 파라미터.

## 28. ★★★ Activity(타임라인) 배치 조회 엔드포인트 부재

**문제** — `/v3/object/activity`가 단일 objectId만 받음. 여러 레코드 타임라인을 한 번에 조회할 배치가 없고, `/v3/object/read`에 activity 인라인 파라미터도 없음.

**실제 영향** — N개 레코드 활동 = N회 호출. "리드 87건 팔로업 이력" = 87콜.

**로그/VOC** — list-engagements가 **최다 호출(6,703콜)**, `engagements→engagements` 연속 **6,385회**. p90 **7.9초**, 5초 초과 20.9%, **429 52건 전부 이 도구**.

**레퍼런스 — HubSpot**: engagement 독립 오브젝트라 batch/read 다건 조회.

**현재 우회와 비용** — 유형 필터·limit·htmlBody 제거로 응답 경량화(2026-07). **N=N콜 구조는 백엔드 확인 결과 해소 불가**(단일 objectId만 수용).

**API 개선안** — `/v3/object/read`에 activity 인라인 파라미터, 또는 배치 activity 엔드포인트. → 87콜 → 1콜.

## 29. ★★ 견적서 발행(공유 링크 생성) API 부재

**문제** — 견적서 엔드포인트가 생성·조회 2개뿐. 발행(publish)·발송·수정·삭제 없음. 발행은 GUI 전용.

**실제 영향** — API로 만든 견적서는 고객 전달용 `공유 링크`가 안 생겨 이메일 첨부 URL 자체가 없음. "AI가 견적서 만들어 발송"이 **구조적 완결 불가** — 견적 자동화의 최종 장벽.

**로그/VOC** — 실측(2026-07): 생성 견적서 `공유 링크` null / `isMainQuote:true`(정상 작동)여도 null(메인 지정≠발행) / `/publish`·`/share`·`/issue` probing 전부 404 / 기존 링크는 전부 GUI 발행분 / 발행 링크는 인증 없이 열리는 공개 페이지.

**레퍼런스 — HubSpot**: Quotes API로 상태 전환(발행) + 공유 URL 응답 포함.

**현재 우회와 비용** — 없음. 발행이 GUI 전용.

**API 개선안** — `POST /v2/quote/{id}/publish`(공유 링크 반환) 또는 생성 시 `publish:true`. → 견적 플로우(생성→발행→발송) API 완결.
