## 읽는 법

각 이슈는 같은 순서로 적습니다.

1. 문제: 지금 API가 무엇을 표현하거나 반환하지 못하는가
2. 실제 영향: 사용자·MCP·LLM이 어떤 일을 못 하거나 잘못할 수 있는가
3. 방향: 문제를 풀기 위해 API가 보장해야 할 결과와 제약

방향은 endpoint 이름이나 내부 구현을 고정하는 명세가 아닙니다. 백엔드가 더 좋은 구조를
선택할 수 있도록, 반드시 지켜야 할 업무 결과와 안전장치만 적습니다.

현재 상태는 공개 API 실측과 코드 확인을 바탕으로 하고, 방향은 MCP 운영 경험에서 나온
제안입니다. 해결된 항목은 본문에서 빼고 맨 아래에 짧게 남깁니다.

## 1. 필요한 레코드를 찾고 비교하기

검색은 CRM 자동화의 시작점입니다. 지금은 조건 검색 자체는 가능하지만, 결과를 비교하거나
많은 후보를 안전하게 찾는 데 필요한 기능이 빠져 있습니다.

### 1-1. 원하는 순서로 결과를 받을 수 없음 ★★★

**문제**
검색에 정렬을 지원하지 않습니다.

**실제 영향**
금액이 큰 딜부터, 최근 만든 고객부터처럼 일상적인 질문에 MCP가 결과를 전부 받은 뒤 직접
정렬해야 합니다. 결과가 많을수록 느리고, cursor를 이어 읽는 동안 기준도 흔들릴 수 있습니다.

**방향**
검색과 목록에 안정적인 정렬 기준과 방향을 제공해야 합니다. 이름, 생성일/수정일, 숫자·날짜
필드 정도는 서버에서 정렬할 수 있어야 합니다.

### 1-2. 조건 없이 전체를 훑을 수 없음.

**문제**
빈 필터로 search를 호출하면 실패합니다.

**실제 영향**
MCP는 전체 목록이 필요한 경우 이름이 존재한다는 의미 없는 조건을 억지로 넣습니다. 호출 의도와
API 입력이 달라져 이해와 유지보수가 어려워집니다.

**방향**
전체 목록을 허용하는 별도 list 경로를 두거나, search에서 빈 조건을 명시적으로 허용해야 합니다.
어느 쪽이든 cursor와 정렬 계약은 같아야 합니다.

### 1-3. 검색 결과로는 비교할 수 없음 ★★

**문제**
검색 결과가 사실상 ID와 이름만 줍니다.

**실제 영향**
금액 1억 이상인 딜을 찾은 뒤에도 금액·담당자·단계가 결과에 없어 다시 읽어야 합니다. 많은
결과를 비교하는 질문은 검색 뒤에 여러 번의 상세 조회가 따라옵니다.

**방향**
호출자가 필요한 필드를 고르면 검색 결과에 함께 돌려줘야 합니다. 기본값은 가볍게 유지하되,
명시한 필드만 추가하는 방식이면 충분합니다.

### 1-4. 커스텀 오브젝트를 같은 방식으로 검색할 수 없음 ★★★

**문제**
커스텀 오브젝트는 공통 검색 경로에서 제외돼 있습니다.

**실제 영향**
기본 오브젝트에는 가능한 조건 검색을 커스텀 오브젝트에는 표현할 수 없습니다. 사용자는 같은
CRM 안의 데이터인데도 UI로 돌아가거나 전체 목록을 읽어야 합니다.

**방향**
커스텀 오브젝트도 기본 오브젝트와 같은 검색 계약을 따라야 합니다. 상품 검색은 #6-1에서 따로 다룹니다.

### 1-5. 여러 이름을 한 번에 정확히 찾을 수 없음 ★

**문제**
문자열 필드에는 여러 값을 정확히 일치시키는 IN 검색이 없습니다.

예를 들어 회사명 80개를 CRM 회사와 정확히 대조하려 해도, 이름 하나씩 조회하거나 전체 회사를
읽는 수밖에 없습니다.

**실제 영향**
실제 MCP 사용 중 회사 전체를 페이지로 읽어 메모리에서 이름을 맞추는 우회(run-script, mcp서버가 api 조합을 대신 돌려주고 결과만 반환)가 있었습니다.
한 번은 약 22.4초, 다른 한 번은 약 20.3초가 걸렸습니다. 지금은 시간 제한 안에 끝났지만,
데이터가 수만 건으로 늘면 시간 초과·메모리 사용·API 부하가 커집니다.

이름 80개를 하나씩 조회하는 방법도 좋지 않습니다. search 호출의 quota 비용 때문에 많은 요청을
짧은 시간에 보내야 하고, 중간 실패가 나면 어느 이름까지 확인됐는지도 복잡해집니다.

**방향**
문자열 배열을 받는 제한된 exact-match 기능이 필요합니다. 이는 포함 검색이나 유사 검색이 아니라
이 이름들 중 하나와 정확히 같은가만 해결하면 됩니다. 빈 배열, 너무 긴 배열, 너무 긴 문자열은
명확히 거절하고, 서버가 중복 값은 정리할 수 있어야 합니다.

MCP 전용 도구가 생기더라도 내부에서 전체 목록을 훑는 방식이면 같은 문제가 남습니다. 서버나 DB가
후보만 찾는 경로여야 합니다.

### 1-6. 표기가 조금 다른 이름에서 후보를 찾기 어려움 ★

**문제**
현재 search는 정확한 필드와 조건을 아는 정형 검색입니다. 삼성전자와 (주)삼성전자처럼 표기가
다르거나, 이메일·전화번호 일부만 아는 경우에는 적절한 후보를 찾기 어렵습니다.

**실제 영향**
LLM은 포함 검색을 여러 번 시도하거나 전체 목록을 읽어 자체적으로 비슷한 값을 찾습니다.
그 결과를 곧바로 쓰기 대상으로 삼으면 비슷한 이름의 다른 레코드를 잘못 고를 위험도 있습니다.

**방향**
정형 search의 의미를 바꾸지 말고, 후보를 찾는 별도 resolve/fuzzy 경로를 두는 편이 안전합니다.
처음에는 회사 이름·도메인, 고객 이름·이메일·전화번호처럼 식별성이 높은 필드만 다루면 됩니다.
결과에는 후보 ID, 표시 이름, 왜 후보가 됐는지 정도를 주고, 실제 변경은 사용자가 후보를 고른 뒤
기존 ID 기반 읽기·쓰기로 이어져야 합니다.

Attio MCP는 정형 목록 조회와 fuzzy 후보 탐색을 분리합니다. HubSpot hosted MCP는 정형 filter와
문자열 query를 함께 받지만, 이것을 fuzzy/semantic 검색으로 설명하지는 않습니다.
[Attio MCP](https://docs.attio.com/mcp/overview),
[HubSpot hosted MCP](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server)

## 2. CRM 업무 기능을 API로 실행하기

### 2-1. 시퀀스: 조회, 등록/해제, 생성/수정이 따로 막혀 있음 ★★★

시퀀스는 이메일·SMS·알림톡·TODO를 정한 순서와 시점에 실행하는 아웃바운드 자동화입니다.
이 항목의 필요 순서는 조회, 등록/해제, 생성/수정입니다. 시퀀스를 직접 만들 수 있더라도
누구에게 어디까지 발송됐고 성과가 어떤지 보지 못하면 운영할 수 없기 때문입니다.
시퀀스 자체 삭제는 이번 범위에 넣지 않습니다.

**문제**

| 현재 경로 | 할 수 있는 일 | 부족한 점 |
|---|---|---|
| 시퀀스 목록·단건 | ID, 이름, 설명, 생성일 확인 | 폴더·소유자·상태·성과·검색·정렬이 없음 |
| 단계 조회 | 단계 유형과 실행 일정 확인 | 발신자와 수정 가능한 콘텐츠 정보가 부족함 |
| 등록 목록 | 등록 ID, 고객 ID, 등록 시각 확인 | 진행 상태·현재 단계·마지막 결과가 없음 |
| 등록 타임라인 | 한 등록 건의 발송/open/click/reply event와 이메일 ID 확인 | 시퀀스 전체의 등록자·이벤트를 한 번에 찾거나 집계할 수 없음 |
| 쓰기 | 없음 | 생성, 수정, 대량 등록, 등록 해제가 안 됨 |

발송된 이메일은 이미 시퀀스와 연결돼 있습니다. 시퀀스, 등록, 등록 단계, 이메일 ID 순서로
따라가면 기존 이메일 상세 API에서 제목과 본문을 읽을 수 있습니다. 따라서 새 시퀀스 API가
발송된 이메일 본문을 중복해서 담을 필요는 없습니다. 문제는 시퀀스 하나에서 그 이메일들을
찾는 목록과 성과 집계가 없다는 것입니다.

**실제 영향**
이 시퀀스의 2단계 이메일을 받은 사람 중 많이 열어본 고객은 누구인가를 답하려면 등록자를
전부 읽고, 각 등록자의 타임라인을 다시 읽고, 이메일·open·click을 메모리에서 맞춰야 합니다.
운영자가 가장 먼저 보고 싶은 진행 상태와 성과가 가장 비싼 조회가 됩니다.

**방향**

1. **조회부터 완성합니다.**
   시퀀스 목록은 폴더·소유자·상태·이름 검색·정렬을 지원하고, 각 행에는 단계 수, 진행/완료/해제
   등록 수, 발송/open/click/reply/bounce/error 요약과 집계 시각을 보여줘야 합니다.
   상세는 단계의 일정·채널·발신자·콘텐츠 참조를, 등록 목록은 대상·실제 수신 고객·상태·현재 단계·
   마지막 결과를 보여줘야 합니다.
   시퀀스 전체 activity/delivery 목록은 기간·이벤트·단계·대상으로 거르고 최신순으로 읽을 수
   있어야 하며, 필요한 이메일만 기존 이메일 상세 API로 열 수 있도록 이메일 ID를 반환해야 합니다.

2. **통계는 시퀀스 API가 직접 제공합니다.**
   이메일 목록 API는 개별 이메일을 찾는 용도입니다. 시퀀스와 단계별 sent/opened/clicked/replied/
   bounced/errored 수와 비율은 시퀀스 API가 계산해야 합니다. 비율의 분모와 집계 시각도 함께
   알려야 합니다. 현재 내부 통계가 누적 cache라면, 첫 공개 범위는 전체 누적값과 계산 시각만으로
   시작하고 기간별 통계는 다음 단계로 나눌 수 있습니다.

3. **그다음 고객·회사·리드·딜을 batch로 등록하고 해제합니다.**
   등록은 단순 레코드 생성이 아닙니다. 발신 계정, 연락처 유무, 수신 거부/bounce, 중복, 권한,
   quota를 확인하고 이후 실행 job을 큐에 넣습니다. 그래서 batch 요청은 입력별로 queued, skipped,
   failed 결과와 사유를 반환해야 합니다.
   현재 UI는 고객·리드·딜만 등록 대상으로 쓰며, 리드/딜에는 실제 수신 고객이 필요합니다.
   회사는 현재 대상이 아닙니다. 하지만 공개 API가 회사를 받는다면 클라이언트가 고객을 임의로
   전개하면 안 됩니다. 연결된 모든 고객에게 발송 또는 명시한 고객에게만 발송처럼 수신자 정책을
   요청에 쓰고, 서버가 실제로 전개한 고객별 결과를 돌려줘야 합니다. 첫 번째 고객을 자동으로
   고르는 규칙은 두지 않아야 합니다.

4. **등록 해제는 삭제가 아니라 이력을 남기는 상태 변경입니다.**
   이후 발송 job을 멈추고 해제 시각·사유를 남기되, 이미 보낸 이메일과 open/click/reply 이력은
   보존해야 합니다. 통계에도 해제 수를 별도로 보여줘야 운영 기록이 사라지지 않습니다.

5. **생성과 수정은 마지막에 엽니다.**
   전용 이메일 템플릿 CRUD가 먼저 있어야 하는 것은 아닙니다. 시퀀스 단계에 제목·본문을 직접
   넣고 수정할 수 있으면 첫 공개 계약은 완결됩니다. 첨부는 이번 범위에서 제외합니다.
   내부 emailSenderId는 실제 발신 계정 ID가 아니라 사용자 ID입니다. 한 사용자가 여러 연동
   계정을 가질 수 있으므로, 공개 API에서는 발신 가능 목록에서 얻은 안정적인 senderId를 선택하게
   하는 편이 맞습니다.
   이미 등록된 고객의 단계는 등록 당시 콘텐츠를 snapshot으로 저장합니다. 따라서 시퀀스 수정이
   기존 등록분까지 바꾸는지, 이후 등록분에만 적용하는지는 반드시 명시해야 하며, 기본은 이후
   등록분에만 적용하는 편이 안전합니다.

HubSpot도 시퀀스의 목록/상세, enrollment, 발신 사용자 identity를 분리해 다룹니다.
[HubSpot Sequences API](https://developers.hubspot.com/docs/api-reference/latest/automation/sequences/guide)

### 2-2. 필드 설정을 수정할 수 없음 ★

**문제**
필드는 만들 수 있지만, 기존 필드의 옵션·라벨·설정을 API로 바꿀 수 없습니다.

**실제 영향**
기능 카테고리에 새 옵션을 추가하거나 필드 설명을 고치는 작업은 전부 UI에서만 해야 합니다.
데이터 이관이나 반복적인 설정 작업도 자동화할 수 없습니다.

**방향**
필드의 생성·조회와 별도로 수정 API가 필요합니다. 어떤 설정을 바꿀 수 있는지, 이미 데이터가
있을 때 어떤 변경이 막히는지는 구조화된 오류로 알려야 합니다.

### 2-3. 중복 레코드를 병합할 수 없음 ★★

**문제**
고객·회사·딜 같은 중복 레코드를 하나로 합치는 공개 API가 없습니다.

**실제 영향**
중복은 웹폼, CSV, 수동 입력에서 계속 생깁니다. 검색으로 후보를 찾을 수 있어도 실제 병합은
UI에서만 해야 하므로 대량 정리가 멈춥니다.

**방향**
어느 레코드를 남길지, 어떤 활동·관계·필드를 옮기는지 명시하는 병합 기능이 필요합니다.
병합은 되돌리기 어려우므로 대상 검증, 권한, 결과 이력이 중요합니다.

### 2-4. 고객 그룹·리드 그룹 관련 ★★★

**문제**
필드에는 고객 그룹과 리드 그룹 타입이 있지만, 공개 API에는 그룹 목록·검색 경로가 없습니다.
또한 그룹은 읽기 전용 필드로 새로 생성하거나, 그룹에 새로 추가하거나 뺄 수도 없습니다.

**실제 영향**
그룹 필드를 읽을 수 있어도 새 값을 넣거나, 특정 그룹을 기준으로 자동화를 만들 수 없습니다.
LLM은 ID와 표시 이름을 발견할 방법 자체가 없습니다.

**방향**
고객 그룹과 리드 그룹의 목록·페이지네이션·이름 검색이 필요합니다. 필드 스키마도 이 값들을
어디서 어떤 형태로 가져오는지 알려야 합니다(#4-5).
그룹 생성 수정도 필요합니다.

데이원컴퍼니에선 이런 작업을 하길 원합니다.

1. 자연어로 콜드메일 보내고 싶은 세그먼트 설명(대기업, HR 담당자, 매출 100억 이상)
2. 필드 조회 -> 회사.유형 고객.직무 회사.매출 필드 조합하여 필터 검색
3. 나온 리스트를 고객으로 묶어놓기
4. (UI에서 직접 해당 리스트를 한번 쭉 점검한 다음)
5. 수동으로 시퀀스에 등록

### 2-5. 발신 계정 목록이 없어 이메일 발송 API를 MCP에서 쓸 수 없음

**문제**
`POST /v2/email`로 이메일을 보낼 수는 있지만, 요청에 `provider`를 넣어야 합니다. 공개 API에는
이 워크스페이스에서 실제로 발신 가능한 연동 계정 목록이 없습니다. 연결된 계정의 이메일 주소,
표시 이름, 사용 가능 상태, 안정적인 식별자를 알 수 없으므로 여러 계정이 있을 때 무엇을 골라야
하는지 표현할 수 없습니다.

**실제 영향**
현재 MCP에는 이메일 발송 도구를 만들지 않았습니다. LLM이 `provider`를 추측하거나 임의의 계정을
기본값으로 고르면, 의도하지 않은 계정에서 고객에게 이메일이 발송될 수 있습니다. 잘못된 값을
보내도 사용 가능한 발신 계정 후보를 구조적으로 돌려주지 않아 사용자가 바로 고칠 수도 없습니다.

**방향**
먼저 발신 가능한 계정 목록을 읽는 경로가 필요합니다. 각 계정은 이메일 주소, 표시 이름, 사용 가능
상태와 안정적인 `senderId`를 보여줘야 합니다. 실제 발송은 `provider`를 추측하는 대신 이 `senderId`를
지정하게 해야 합니다.

사용 가능한 계정이 정확히 하나일 때만 서버가 자동 선택할 수 있습니다. 둘 이상이면 호출자가
`senderId`를 명시해야 하며, 없거나 사용할 수 없는 값을 보낸 경우에는 오류 코드와 함께 선택 가능한
계정 목록을 반환해야 합니다. 이 계약이 있어야 MCP가 이메일 발송을 도구로 안전하게 제공할 수 있습니다.

## 3. 액티비티를 찾고 읽고 쓰기

여기서 활동은 고객·회사·딜·리드 타임라인에 보이는 이메일, 노트, TODO, 녹음, 자동 이벤트 등을
말합니다. 공개 API의 조회 노출은 두 가지입니다.

- **완전 독립 액티비티 목록**: 노트나 TODO처럼 활동 자체를 한 행씩 찾습니다. 메인 레코드와 연결되지
  않은 활동도 이 목록에 남을 수 있습니다. 현재는 유형별 API일 뿐, 모든 활동을 합친 `list-activities`는 없습니다.
- **메인 오브젝트 연결 액티비티 목록**: 고객·회사·딜·리드·커스텀 오브젝트에 연결되어 타임라인에 보이는
  활동을 찾습니다. 상위 레코드 ID를 생략하면 해당 메인 오브젝트 종류 전체, 지정하면 한 레코드의 360도
  타임라인이 됩니다.

내용을 읽고, 만들거나 고치는 경로는 활동 유형마다 다릅니다.

### 3-1. 활동 유형마다 다음에 할 수 있는 일이 다름

#### 현황: 공개 API에서 활동을 찾고 읽고 바꾸는 방식

이 표는 2026-08-06 기준 공개 V2 API의 현재 상태만 적습니다. MCP가 상세 API를 다시 불러 제목·미리보기를
붙이는 동작은 포함하지 않습니다.

`GET /v2/{object}/activity`는 메인 오브젝트 연결 액티비티 목록입니다. 고객·회사·딜·리드·커스텀
오브젝트별로 따로 있고, `{object}Id`는 선택 필터입니다. ID를 생략하면 해당 메인 오브젝트 종류 전체의
활동을, ID를 넣으면 한 레코드의 360도 타임라인을 반환합니다. 두 경우 모두 유형·기간·cursor를 받고,
정렬은 cursor 기준 오래된 순으로 고정돼 있습니다. 다섯 목록을 합친 단일 activity stream은 아닙니다.

`상세 조회`가 `없음`인 행은 타임라인에 유형이나 ID가 보여도 그 활동의 실제 본문·내용을 읽는 공개 단건
API가 없다는 뜻입니다.

현재 MCP의 `salesmap-list-engagements`는 `objectId`를 필수로 두고 있어, 원본 API의 메인 오브젝트 종류
전체 목록 모드는 아직 MCP 도구로 열려 있지 않습니다.

| 활동 (V2 type) | 완전 독립 액티비티 목록 | 메인 오브젝트 연결 액티비티 목록 | 상세 조회 (본문·내용) | 생성 | 수정 | 삭제 |
|---|---|---|---|---|---|---|

| 이메일 link click (`emailLinkClick`) | 없음 - event 자체 목록 없음 | 있음 - 메인 오브젝트 종류 전체 또는 한 레코드 | 없음 - 원 이메일만 열 수 있음 | 없음 - 자동 event | 없음 | 없음 |

| 카카오 알림톡 (`kakaoAlimtalkSend`) | 없음 | 있음 - 메인 오브젝트 종류 전체 또는 한 레코드 | 없음 - 공개 상세 API 없음 | 없음 | 없음 | 없음 |
| 녹음/AI 녹취 (`recordingCreate`) | 없음 - 녹음 자체 목록 없음 | 있음 - 메인 오브젝트 종류 전체 또는 한 레코드 | 있음 - 녹음 상세·녹취 전문 | 없음 | 없음 | 없음 |
| 일정 (`meeting`) | 없음 | 있음 - 메인 오브젝트 종류 전체 또는 한 레코드 | 없음 - 공개 상세 API 없음 | 없음 - 일정 모듈 공개 API 없음 | 없음 | 없음 |
| 레코드 생성 (`create`) | 없음 | 있음 - 메인 오브젝트 종류 전체 또는 한 레코드 | 없음 - 원래 레코드만 열 수 있음 | 없음 - 자동 event | 없음 | 없음 |

| 병합 (`merge`) | 없음 | 있음 - 메인 오브젝트 종류 전체 또는 한 레코드 | 없음 - 원래 레코드만 열 수 있음 | 없음 - 병합 API도 없음 (#2-3) | 없음 | 없음 |
| 모두싸인 계약 생성 (`modusignContractCreated`) | 없음 - 계약 자체 목록 없음 | 있음 - 고객·회사·딜 전체 또는 한 레코드 | 없음 - 공개 상세 API 없음 | 없음 - 연동 자동 event | 없음 | 없음 |

- 메인 오브젝트 연결 액티비티 목록에서 `webFormView`와 `documentView`는 고객만, `webFormSubmit`은
  고객·회사·딜·리드만, `modusignContractCreated`는 고객·회사·딜만 나옵니다. 이 네 유형은 커스텀
  오브젝트 activity에 없습니다.
- activity 행의 ID 필드도 오브젝트 테이블마다 다릅니다. 고객 activity에는 `documentId`·`documentName`이 있지만
  meeting/알림톡 ID는 없고, 커스텀 오브젝트 activity에는 `meetingId`·`kakaoAlimtalkId`·`emailLinkId`가 있습니다.
  현재 이 ID들로 이어지는 공개 상세 API는 없습니다.

#### 웹폼·문서는 활동이 아닌 별도 리소스

| 대상 | 공개 목록 | 공개 단건·하위 목록 | 활동 타임라인과의 관계 |
|---|---|---|---|
| 웹폼 | `GET /v2/webForm`로 폼 목록 조회 (현재 cursor를 실제로 받지 않음) | 알고 있는 웹폼 ID로 제출 목록 조회 | 폼 자체는 activity가 아님 |
| 웹폼 제출 | 전역 제출 목록 없음 | `GET /v2/webForm/{webFormId}/submit` - 반드시 웹폼 ID 필요 | 제출은 일부 상위 레코드의 `webFormSubmit` event로 보일 수 있지만, 이 목록은 완전 독립 액티비티 목록이 아님 |
| 문서 | 없음 - 문서 목록 API 없음 | 없음 - `documentId` 단건 조회·문서별 조회자 목록 API 없음 | 문서 자체는 activity가 아님. 고객 activity의 `documentView` 행에만 `documentId`·`documentName`이 보일 수 있음 |

완전 독립 목록과 메인 오브젝트 연결 목록, 그리고 상세·쓰기 경로는 이렇게 다릅니다. 특히 이메일·녹음처럼
독립 목록이 없는 유형은 메인 오브젝트 연결 activity 행을 다시 조합해야 합니다.

| 생성 event | 타임라인 | 원래 레코드 상세 조회 | event 자체를 독립적으로 읽는 요구는 낮음 |
| 웹폼 조회 | 고객 타임라인 | 없음 | 실제 조회가 activity로 남는 조건이 불명확함 |
| 웹폼 제출 | 타임라인과 폼 제출 목록 | 알고 있는 폼의 제출 목록 조회 | 안정적인 폼 식별 정보가 필요함 |
| 문서 조회 | 고객 타임라인의 documentId·documentName | 없음 | 문서 단건·조회자 목록 API가 없음 |
| 병합 event | 타임라인 | 원래 레코드 조회 | 병합 기능 자체가 공개 API에 없음(#2-3) |
| 모두싸인 계약 생성 | 고객/회사/딜 타임라인 | 없음 | 계약을 식별하거나 목록으로 보는 경로가 없음 |

**실제 영향**
LLM은 activity type 하나만 보고 상세가 있을 것, 수정할 수 있을 것, 전역에서 찾을 수 있을 것이라고
추측하기 쉽습니다. 하지만 현재는 노트·이메일·녹음처럼 일부만 상세가 있고, TODO·SMS·알림톡은
다음 단계가 막힙니다.

**방향**
모든 활동을 같은 거대한 CRUD로 만들 필요는 없습니다. 먼저 각 유형에 대해 다음 세 가지를
명확히 해야 합니다.

- 타임라인에서 찾은 ID로 무엇을 읽을 수 있는가
- 완전 독립 액티비티 목록이 필요한 유형은 무엇인가
- 생성·수정이 필요한 유형은 무엇인가

일반 activity 응답은 ID·시각·연결 레코드처럼 가볍게 유지하고, 필요한 상세만 별도 조회하거나
MCP가 조합하면 됩니다. 활동 삭제와 일괄 삭제는 이번 1차 요구에 넣지 않습니다.

#### 이메일: 최근 반응한 고객을 찾을 수 없음 ★

**문제**
이메일 한 건은 읽을 수 있지만 이메일 전체를 기간·참여자·연결 레코드로 목록화하거나 검색할 수
없습니다.

**실제 영향**
원본 API에서는 다섯 메인 오브젝트 연결 액티비티 목록을 기간·유형으로 각각 읽어 이메일·open·click event를 합칠 수는
있습니다. 그러나 목록이 고객·회사·딜·리드·커스텀 오브젝트별로 갈리고, 이메일 한 건 단위의 제목·참여자·
open/click 집계가 없습니다. 딜이나 리드에만 연결된 이메일을 어느 고객의 성과로 볼지도 호출자가 정해야 합니다.

현재 MCP는 `objectId`를 필수로 둬 이 메인 오브젝트 종류 전체 목록 모드도 쓰지 못합니다. 그래서 MCP에서는 고객을
하나씩 읽고 각 타임라인을 호출해 합산하는 우회가 여전히 필요합니다.

**방향**
이메일 전역 목록은 이메일 한 건을 한 행으로 보여주고, 제목·본문·참여자·연결 레코드·발송 시각과
open/click 집계를 함께 반환해야 합니다. 반대로 개별 발생 시각을 보는 일은 공통 activity 검색에서
open/click event로 봅니다.

#### 노트와 TODO: 업무 기록을 끝까지 관리할 수 없음 ★★★

**문제**
노트는 목록과 상세가 비교적 잘 되어 있지만, 생성은 레코드 수정의 memo 입력을 빌려야 합니다.
TODO는 목록만 있고 생성·수정·단건 조회가 없습니다.

**실제 영향**
노트를 과거 날짜나 다른 작성자 이름으로 남길 수 없고, 미팅 후 해야 할 일을 팀원에게 배정하거나
완료로 바꾸는 기본 업무를 API로 할 수 없습니다.

**방향**
노트는 본문·유형·발생 시각·작성자·연결 레코드를 지정하는 독립 생성/수정 기능이 필요합니다.
TODO는 제목·내용·담당자·기한·완료 여부·연결 레코드를 읽고 쓰는 기본 lifecycle이 필요합니다.

#### 녹음: 찾을 수 없고, 긴 녹취는 안전하게 읽을 수 없음 ★

**문제**
녹음 ID를 알고 있으면 상세와 녹취를 읽을 수 있지만, 이번 주 담당자 A의 딜 관련 녹음처럼
기간·담당자·연결 레코드로 찾을 수 없습니다. 녹음 상세에도 연결 레코드 ID가 없습니다.

**실제 영향**
원본 API에서는 다섯 메인 오브젝트 연결 액티비티 목록을 `recordingCreate`로 읽어 녹음 ID를 모을 수는 있습니다. 하지만
녹음 자체의 기간·담당자·연결 레코드 목록은 아니며, 결과를 object table별로 합쳐야 합니다. 현재 MCP는
`objectId`를 필수로 둬 이 모드도 쓰지 못하므로 레코드를 하나씩 돌며 타임라인을 뒤집니다. 또한 녹취는 현재
상한 없이 전부 반환됩니다.
실측 59분 회의는 404개 segment, 약 20,687자와 85KB였습니다. 긴 회의는 요청 시간과 메모리를
불안정하게 만듭니다.

**방향**
녹음은 기간·담당자·연결 레코드로 찾는 목록과, 상세의 연결 레코드 ID가 필요합니다. 녹취는
시간 구간 검색까지 요구하지 않습니다. 일정한 최대 크기까지 전문을 반환하고, 넘으면 cursor로
다음 부분을 읽게 하면 충분합니다.

#### 웹폼·문서·자동 event: 필요한 식별 정보만 안정적으로 ★

웹폼 제출과 문서 조회는 독립 전역 목록을 먼저 만들 필요는 없습니다. 웹폼 제출에는 폼 ID와
이름을 안정적으로 싣고, 알고 있는 폼의 제출 목록을 여는 방식이면 됩니다. 문서 조회도 문서 ID와
이름을 주면 됩니다.

웹폼 조회는 예외입니다. 기존 activity 행을 읽을 수 있는 것과 새 웹폼 조회가 activity로 남는 것은
다른 문제입니다. 공개 activity로 유지한다면 어떤 조회가 언제 타임라인에 기록되는지 계약으로
정해야 합니다.

모두싸인 계약 생성은 연결 레코드의 타임라인뿐 아니라 계약을 식별하고 목록으로 볼 수 있는 별도
경로가 필요합니다.

HubSpot은 이메일·노트·TODO 같은 핵심 활동을 각각 독립 object로 다룹니다. 세일즈맵이 모든
활동을 똑같이 만들 필요는 없지만, 전역으로 찾아야 하거나 lifecycle이 필요한 유형은 같은 수준의
목록·상세·batch read를 갖추는 방향이 참고가 됩니다.

### 3-2. 고객 활동 복사 옵션이 UI에만 있음 ★★

**문제**
현재 UI는 고객을 새 리드나 딜에 연결할 때, 고객의 기존 활동을 모두 또는 일정 기간만 복사할 수
있습니다. 공개 v2/v3 생성 API에는 이 선택이 없습니다.

이 기능은 모든 관계에서 활동이 자동으로 보이는 일반 규칙이 아닙니다. 현재 일반 UI에서 확인된
범위는 고객에서 새 리드/딜로 가는 경우뿐입니다. 회사 활동을 고객·딜로 자동 복사하는 공개 동작은
없습니다.

**실제 영향**
UI로 만든 리드/딜과 API로 만든 리드/딜의 타임라인이 달라집니다. 이 고객의 최근 이메일 이력도
새 딜에서 보이게 해달라는 요청을 API로 표현할 수 없습니다.

**방향**
관계 전체를 일반화하지 말고, UI와 같은 고객에서 리드/딜로의 복사만 좁게 공개하는 편이 맞습니다.
전체·최근 30일·지정일 이후 중 어느 범위를 복사할지 고르고, 비동기 작업의 상태를 함께 반환해야
합니다.

### 3-3. 최근 활동을 바로 볼 수 없음 ★★★

**문제**
레코드 activity는 오래된 순서로만 반환됩니다.

**실제 영향**
한 페이지가 50건인 것은 문제가 아닙니다. 문제는 이 고객의 최근 활동이 첫 페이지에 없다는
점입니다. 최근 50건을 보려면 cursor를 끝까지 따라가거나 날짜를 추측해 좁혀야 합니다.

**방향**
최신순 정렬만 지원하면 됩니다. 최근 50건을 먼저 주고, 더 필요할 때 cursor를 이어 읽는 구조면
충분합니다.

### 3-4. 타임라인 상세를 한 번에 읽을 수 없음 ★★★

**문제**
타임라인 한 페이지에는 노트 ID·이메일 ID·녹음 ID만 있고, 제목·본문 미리보기·AI 요약은 각각
단건 상세 API를 다시 호출해야 합니다.

**실제 영향**
활동 50개가 있는 고객 한 명을 읽을 때 타임라인 1회와 상세 최대 50회가 필요합니다.
2026-06 telemetry에서 list-engagements는 6,703회로 가장 많이 호출됐고, 연속 호출은
6,385회였습니다. p90은 7.9초, 20.9%는 5초를 넘었습니다.

**방향**
여러 고객의 타임라인을 한 요청으로 섞자는 뜻이 아닙니다. cursor는 고객별로 남겨 둡니다.
대신 이미 찾은 노트·이메일·녹음 ID를 묶어 상세를 읽는 batch 경로가 필요합니다.

기본 응답은 노트 미리보기, 이메일 제목·참여자·짧은 내용, 녹음 제목·길이·AI 요약 정도면 됩니다.
긴 이메일 본문과 녹취 전문을 무조건 batch로 보내면 안 됩니다. 항목별 실패는 전체 batch 실패가
아니라 각 ID의 오류로 반환해야 합니다.

### 3-5. 날짜 끝 경계가 달라 노트가 조용히 빠짐 ★

**문제**
activity 날짜 필터는 한국 날짜 기준인데, 노트 목록의 종료일은 UTC 자정으로 해석됩니다.

**실제 영향**
종료일을 2026-07-31로 조회하면 7월 31일 낮에 만든 노트도 빠질 수 있습니다. 요청은 200으로
성공하므로 사용자는 누락을 알아채기 어렵습니다. telemetry에서 날짜 필터를 쓴 노트 조회 29회 중
종료일을 쓴 22회가 이 영향을 받았습니다.

**방향**
같은 날짜 입력은 activity와 노트에서 같은 한국 날짜 범위를 뜻해야 합니다. 종료일은 그 날의 끝까지
포함하고, 날짜와 시각을 섞는 규칙도 문서화해야 합니다.

### 3-6. meeting은 회의록이 아니라 일정 모듈 이벤트임

**문제**
meeting activity는 일반 회의록이나 통화 기록이 아닙니다. 세일즈맵의 Calendly형 일정 모듈에서
일정을 잡고, 초대·알림·재알림을 운영할 때 남는 이벤트입니다. 회의 내용은 이곳에 저장되지 않습니다.

**실제 영향**
LLM은 meeting이 없으면 회의가 전혀 없다고 판단하거나, meeting이 있으면 회의록을 읽으려 합니다.
일정 변경을 일반 activity 수정처럼 추측해 호출할 위험도 있습니다.

**방향**
먼저 제품 경계를 정해야 합니다. 일정 모듈을 공개한다면 일정 상태·시간·참석자·초대·알림을 다루는
별도 API/MCP 도구가 필요합니다. 그렇지 않다면 MCP에서 meeting을 일반 engagement로 오해하지 않게
하고, 일정은 TODO, 회의 내용은 노트에 남기는 패턴을 분명히 해야 합니다.

## 4. CRM 기본 관리·필드 정보

### 4-1. 삭제 기능의 범위와 실패 이유가 불명확함

**문제**
삭제 경로와 요청 형식이 일반적이지 않고, 실제로는 리드/딜만 지원합니다. 시퀀스에 등록된 레코드를
삭제하면 이유 없이 실패할 수 있습니다.

**실제 영향**
MCP는 고객·회사·커스텀 오브젝트도 같은 방식으로 삭제될 것이라고 기대할 수 있고, 실패했을 때
사용자에게 무엇을 먼저 해결해야 하는지 설명할 수 없습니다.

**방향**
삭제를 지원하는 타입과 지원하지 않는 타입을 명확히 해야 합니다. 지원하지 않는 경우에는 안정적인
이유를, 시퀀스 등록처럼 사전 조건이 있는 경우에는 해제 방법을 돌려줘야 합니다. 상품·견적서의
삭제는 리뉴얼 묶음 #6에서 다룹니다.

### 4-2. 필드 조회만으로는 안전하게 읽고 쓸 수 없음 ★★

**문제**
필드 스키마는 이름·타입·일부 선택지 정도만 줍니다. 이 정보만으로는 이 필드에 값을 써도 되는가,
API가 꼭 요구하는가, 어떤 형식으로 보내야 하는가를 알 수 없습니다.

특히 현재 required는 생성 화면에서의 필수 표시와 API 생성의 필수 검증이 섞여 있습니다.
LLM이 이를 보고 값을 지어 넣거나, 실제 API 필수값을 추측하면 안 됩니다.

**실제 영향**

| 알아야 하는 것 | 지금 생기는 문제 |
|---|---|
| 시스템 필드인지, 커스텀 필드인지 | 어떤 필드가 제품이 관리하는 값인지 알 수 없음 |
| 계산값·자동값·읽기 전용인지 | 총 매출, 마감일 같은 값에 써도 되는지 미리 판단할 수 없음 |
| API에서 실제 필수인지 | 생성 화면의 관행을 API 검증으로 잘못 이해할 수 있음 |
| 유니크·민감 필드인지 | 중복·개인정보 제약을 모른 채 입력 계획을 세움 |
| 입력 위치와 값 형태 | top-level인지 fieldList인지, ID인지 배열인지 MCP가 하드코딩으로 추측함 |
| 화면에서 어떻게 쓰이는지 | 선택적으로 참고할 UI 노출·순서 정보가 없음 |
| 실제 채움률 | 어떤 필드가 실제 운영에 쓰이는지 알 수 없음 |

백엔드에는 설명, formula, 유니크, 민감도, 화면 노출·순서 등 일부 정보가 이미 있습니다. 반면
자동 채움 규칙과 채움률은 새 설계가 필요합니다.

**방향**

- API 쓰기 규칙: writable 여부, 실제 생성/수정 필수 여부, 값 위치, 값 형태, 단일/복수 여부,
  읽기 전용 이유를 스키마에서 알려야 합니다.
- UI 힌트: 생성 화면 노출·필수·순서는 API 쓰기 규칙과 분리해야 합니다. 이는 값을 지어 넣는
  근거가 아니라 사용 맥락을 이해하는 힌트입니다.
- 자동 규칙: 예를 들어 딜 마감일처럼 상태에 따라 자동으로 채워지거나 비워지는 필드는
  선행 조건과 자동 동작을 설명해야 합니다.
- 채움률: 목록 스키마마다 전체 레코드를 세지 말고, 필요할 때 별도 통계로 값 존재 수·비율·집계
  시각만 제공하면 됩니다.

HubSpot도 property 정의에서 설명, 시스템 원천, 계산 여부, unique, 읽기 전용, 참조 대상을
구분합니다. 반면 UI form 정보와 실제 생성 필수값은 별도 모델이므로, 세일즈맵도 하나의 required
값에 섞지 않아야 합니다.

### 4-3. 같은 사용자를 두 API가 다르게 설명함

**문제**
현재 사용자 조회와 사용자 목록 조회가 email, role, room, status 표현을 다르게 반환합니다.

**실제 영향**
MCP가 현재 사용자의 이메일을 알아야 하면 사용자 목록을 다시 읽어 ID로 맞춰야 합니다.
상태 값도 한쪽은 한글, 한쪽은 영어라 프로그램 비교가 흔들립니다.

**방향**
같은 사용자라면 공통 필드와 enum 형식을 맞춰야 합니다. 현재 사용자에게만 필요한 workspace
정보가 있다면 목록과 단건의 차이를 문서화하되, email·role·status처럼 공통인 값은 일관돼야 합니다.

### 4-4. IP 제한을 켠 워크스페이스에서는 MCP가 작동하지 않음

**문제**
MCP는 중간 서버를 거쳐 세일즈맵 API를 호출합니다. IP 제한을 켠 고객은 자기 사무실 IP가 아니라
MCP 서버의 출발 IP가 차단되므로 모든 호출이 실패합니다.

2026-06-05 실제 고객 워크스페이스에서는 호출마다 다른 출발 IP가 보이며 허용되지 않은 IP 오류가
반복됐습니다.

**실제 영향**
보안 설정을 켠 고객은 MCP 자체를 사용할 수 없습니다. API 키와 권한이 정상이어도 첫 요청부터
실패합니다.

**방향**
고객이 허용할 수 있는 고정 출발 IP를 제공하거나, 고객이 명시적으로 허용한 MCP 전용 인증 경로를
설계해야 합니다. 단기적으로는 API용 IP 제한 해제가 유일한 우회입니다. 어떤 방식을 택하든
고객이 보안 정책을 포기하지 않고 MCP를 쓸 수 있어야 합니다.

### 4-5. 참조형 필드가 값을 어디서 가져오는지 알려주지 않음 ★

**문제**
선택형 필드의 선택지는 스키마 안에 있어도 자연스럽습니다. 하지만 담당자, 팀, 파이프라인,
시퀀스, 웹폼처럼 다른 리소스를 가리키는 필드는 값의 출처와 입력 형태가 스키마에 없습니다.

**실제 영향**
LLM은 타입 이름을 보고 어떤 목록 API를 호출할지, ID를 넣을지 이름을 넣을지, 배열인지 단일값인지
추측해야 합니다. 고객 그룹과 리드 그룹은 목록 API도 없어 값을 발견할 수 없습니다(#2-4).

**방향**
모든 후보를 스키마에 넣을 필요는 없습니다. 대신 참조형 필드는 어떤 리소스를 가리키는지, 단일인지
복수인지, 어떤 ID 형태인지, 후보 목록 또는 검색 경로가 무엇인지를 알려야 합니다. 독립 리소스는
별도 목록 API를 계속 쓰면 됩니다.

HubSpot도 enum 선택지는 property 안에 두고, owner·pipeline·association label 같은 큰 리소스는
별도 API로 둡니다. 중요한 점은 스키마가 그 분리를 설명한다는 것입니다.

## 5. API 입력·오류 계약

### 5-1. 읽기·목록 API의 오류를 프로그램이 이해할 수 없음(일관성 없음)

**문제**
v3 생성/수정의 batch 오류는 이미 구조화돼 있습니다. 남은 문제는 object read/list,
association read/list, rate limit 오류가 대부분 문자열뿐이라는 점입니다.

**실제 영향**
MCP는 없는 필드, 없는 관계, 입력 모양이 틀림을 오류 문장으로 추측합니다. 429를 받았을 때도
언제 다시 시도할지, 같은 오류를 운영에서 어떻게 묶을지 알기 어렵습니다.

**방향**
읽기·목록·관계·rate limit 오류에도 안정적인 코드, 문제 위치, 재시도 시각, 요청 ID가 필요합니다.
사람이 읽는 문구는 바뀔 수 있어도 코드와 context는 바뀌지 않아야 합니다.

### 5-2. dateTime에 날짜만 넣으면 호출 시각이 붙음

**문제**
v3 dateTime 필드에 날짜만 보내면 자정이 아니라 API를 부른 시각이 붙어 저장됩니다.

**실제 영향**
같은 입력을 아침에 보내면 아침 시각, 저녁에 보내면 저녁 시각이 저장됩니다. 결과가 재현되지 않고
날짜 범위 조회의 경계에도 영향을 줍니다. date 타입은 같은 입력을 한국 시간 자정으로 처리하므로
두 타입의 차이도 더 헷갈립니다.

**방향**
dateTime은 시각과 UTC offset을 포함한 값을 요구하고, 날짜만 온 경우에는 명확히 거절해야 합니다.
date-only는 date 타입만 받아야 합니다. MCP가 임의로 현재 시각이나 자정을 붙여 의미를 추측하면
안 됩니다.

## 6. 견적서·상품은 리뉴얼 뒤 한 번에 정비

이 섹션은 필요성이 낮아서 뒤에 둔 것이 아닙니다. 견적서·상품 모델 리뉴얼 뒤에 검색, 읽기,
lifecycle, 입력 계약을 한 번에 정하기로 했기 때문에 의도적으로 후순위입니다.
따라서 별을 붙이지 않습니다.

### 6-1. 상품을 찾거나 삭제할 수 없음

**문제**
상품은 조건 검색이 안 되고, 특정 상품을 찾으려면 전체 목록을 읽어야 합니다. 삭제 경로도 없습니다.

**실제 영향**
견적서에 넣을 상품을 자동으로 고르기 어렵고, 테스트나 잘못 만든 상품을 정리할 수 없습니다.

**방향**
리뉴얼 때 상품을 공통 검색에 넣고, 이름·코드 같은 기본 조건으로 찾게 해야 합니다. 삭제와 수정은
상품 lifecycle 전체와 함께 정합니다.

### 6-2. 견적서를 만들 수는 있어도 발행할 수 없음

**문제**
API로 견적서를 만들 수 있지만, 고객에게 보낼 공유 링크를 만드는 발행 기능은 UI에만 있습니다.

**실제 영향**
견적서를 만들고 바로 고객에게 보내달라는 요청은 생성까지만 자동화됩니다. API로 만든 견적서는
공유 링크가 없어 이메일에 넣을 URL도 없습니다.

**방향**
리뉴얼 때 발행과 공유 링크 발급을 견적서 lifecycle의 일부로 다뤄야 합니다. 생성 시 발행할지,
나중에 발행할지, 수정·삭제 후 링크가 어떻게 되는지를 한 계약에서 정하면 됩니다.

### 6-3. 상품 구성을 다시 읽을 수 없음

**문제**
상품의 하위 상품 구성은 만들 수 있지만, 만든 뒤 다시 읽을 공개 경로가 없습니다.

**실제 영향**
MCP는 생성 결과를 검증하거나 기존 상품 구성을 바탕으로 새 견적서를 만들 수 없습니다.

**방향**
상품 상세 또는 전용 구성 조회가 상품 구성 전체를 반환해야 합니다. 쓰기와 읽기 계약이 같은
구조를 사용해야 합니다.

### 6-4. 견적서 상품의 이름과 입력 규칙이 제각각임

**문제**
같은 견적서 상품을 스키마, 오류, 요청 본문이 서로 다른 이름으로 부릅니다. 어떤 값은 필드 목록에
넣어야 하고, 어떤 값은 별도 입력으로 보내야 하는데 스키마만으로는 알 수 없습니다.

**실제 영향**
오류 메시지에 나온 이름으로 스키마를 조회하면 실패할 수 있고, 값 위치가 틀려도 필수값 오류가
먼저 나와 원인을 오해할 수 있습니다.

**방향**
리뉴얼 때 object type, 필드 이름, 값 형식, 입력 위치를 하나의 canonical 계약으로 맞춰야 합니다.
하위 호환이 필요하면 별칭을 허용하되, 잘못된 위치는 안정적인 오류 코드로 바로 알려야 합니다.

## 참고: v3 이관 중 남아 있는 v2 호환 문제

아래 두 항목은 현재 API의 새 이슈가 아니라, MCP가 아직 v2도 지원해야 해서 남은 변환입니다.
T1/T2/T3 우선순위에는 넣지 않습니다.

### L-1. v2는 필드 타입마다 다른 입력 키를 요구함

v3는 필드명과 값을 평탄하게 받지만, v2 수정은 type별 fieldList 값 키를 골라야 합니다.
MCP가 스키마를 읽어 변환하는 이유입니다. v2 수정이 v3 계약으로 이관되면 제거할 수 있습니다.

### L-2. v2는 일부 값을 별도 위치에 넣어야 함

v3는 값을 한 곳에 받지만, v2는 딜의 금액·파이프라인·단계 같은 일부 값을 일반 필드와 다른
위치에 넣어야 합니다. 잘못된 위치는 조용히 무시될 수 있어 MCP가 현재 변환을 유지합니다.
