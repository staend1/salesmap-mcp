# API 레퍼런스 동기화

## 파일 구조

```
docs/salesmap-api-reference-<날짜>.md        원장 아카이브. 받은 그대로. 수정 금지
docs/salesmap-api-reference-legacy.md        구 문서 (2026-02-27 계보). 참고용 보존, 갱신 안 함
docs/internal/api-ref-overlay.md             우리(MCP) 지식. 단일 파일, 항상 최신만 유지
docs/internal/api-ref-merged-<날짜>.md       병합본 아카이브. 이 스킬의 산출물
scripts/build-api-ref.mjs                    최신 병합본 → api-ref.ts
src/tools/api-ref.ts                         생성물. 직접 수정 금지
```

`salesmap-get-api-ref`가 내려주는 문서 = **원장 + 오버레이**.

**날짜는 원장 자신의 "문서 기준일"을 쓴다** (파일 상단에 적혀 있음). 받은 날짜가 아니다. 원장 기준일이 없으면 받은 날짜를 쓰고 그 사실을 보고에 적는다.

원장과 병합본을 **날짜별로 쌓아두는 이유**: 원장이 무엇을 언제 바꿨는지 추적할 수 있고, 문제가 생기면 이전 버전으로 즉시 되돌릴 수 있다 (`node scripts/build-api-ref.mjs 2026-07-28`).

***

## 병합은 LLM이 한다

원장은 **섹션 제목·문구·구조가 통째로 바뀐다.** 실측: 2026-06-30 → 07-28 갱신에서 547줄이 변했고, 표 컬럼 폭·용어("연결관계"→"연관관계")·섹션 신설이 뒤섞여 있었다.

그래서 기계적 문자열 앵커 매칭은 성립하지 않는다. **원장을 읽고, 오버레이의 의도를 이해해서, 적절한 자리에 녹여넣는 판단**이 필요하다. 스크립트는 이스케이프만 담당한다.

## 왜 이 구조인가

과거엔 원장을 복사해 직접 고치는 **포크** 방식이었다. 결과:

- 원장이 갱신돼도 반영되지 않아 우리 문서가 stale해짐
- **2026-07-28 실측**: 파일 API에 대해 "레코드 첨부 불가 / 조회·삭제 API 없음"이라고 단언하고 있었으나 라이브 OpenAPI 확인 결과 **셋 다 존재**했다. `get-api-ref`를 읽은 AI가 고객에게 "그건 안 됩니다"라고 답하고 있었을 가능성이 높다
- 원장과 547줄 차이가 벌어져, 갱신 때마다 "우리 수정"과 "원장 개선"을 손으로 가려내야 했다

오버레이 방식은 우리 것만 따로 관리하므로 원장을 통째로 받아도 안전하다.

***

## 절차

### 1. 원장 아카이브

원장 상단의 **문서 기준일**을 확인해 `docs/salesmap-api-reference-<날짜>.md`로 저장한다. **받은 그대로 저장하고 손대지 않는다.**

직전 원장과의 diff를 떠서 무엇이 바뀌었는지 파악한다 (5번 보고에 쓴다).

```bash
ls docs/salesmap-api-reference-*.md          # 이전 버전 확인
diff -u docs/salesmap-api-reference-<이전>.md docs/salesmap-api-reference-<신규>.md | head -200
```

### 2. 오버레이 항목별로 판단

`docs/internal/api-ref-overlay.md`의 **각 항목마다** 순서대로 확인한다.

**(a) 삭제 조건이 충족됐는가?**
원장이 그 내용을 이미 담게 됐다면 **항목을 삭제한다.** 가장 좋은 결말이다 — 유지보수 비용이 줄고, 원장이 우리보다 정확하다.

**(b) 아직 필요한가?**
필요하면 새 원장의 **어느 위치**에 넣을지 판단한다. 오버레이의 "어디에"는 위치의 *성격*을 서술한 것이지 정확한 좌표가 아니다. 섹션 이름이 바뀌었어도 같은 성격의 자리를 찾는다.

**(c) 문구를 손봐야 하는가?**
원장 용어가 바뀌었다면(예: "연결관계"→"연관관계") 오버레이 본문도 맞춘다. 문서 전체가 일관돼야 한다.

### 3. 병합본 작성

원장을 기반으로 오버레이를 녹여 `docs/internal/api-ref-merged-<날짜>.md`를 만든다. 날짜는 원장과 같은 날짜를 쓴다.

- **원장 내용은 임의로 지우지 않는다.** 덧붙이되 덜어내지 않는다
- 목차·상호참조가 있으면 함께 갱신한다
- 오버레이가 삽입된 자리가 문맥상 자연스러운지 읽어본다

### 4. 빌드 + 검증

```bash
node scripts/build-api-ref.mjs      # 최신 병합본 자동 선택 + 왕복 이스케이프 검증
npx tsc --noEmit && npm run build
```

추가로 **반드시** 확인한다.

- [ ] 오버레이 각 항목이 병합본에 실제로 들어갔는가 (문자열 검색)
- [ ] 원장의 주요 신규 내용이 살아있는가 (1번 diff에서 본 것들)
- [ ] 미공개 API가 새어 들어가지 않았는가 (아래 원칙 참조)
- [ ] 이전 병합본 대비 이유 없이 사라진 내용이 없는가
  ```bash
  diff docs/internal/api-ref-merged-<이전>.md docs/internal/api-ref-merged-<신규>.md | head -100
  ```

> LLM 병합은 비결정적이다. **이 검증을 건너뛰지 말 것.**

### 5. 사용자에게 보고

- 원장에서 새로 들어온 주요 변경 (우리가 몰랐던 API·규칙)
- **삭제한 오버레이 항목** (원장이 흡수한 것 — 좋은 소식)
- **원장이 틀린 것으로 의심되는 것** ← 아래 참조
- 남은 오버레이 개수

## 원칙

1. **원장을 신뢰한다.** 세일즈맵 개발팀이 정기 갱신하는 공식 문서다. 우리 기억보다 우선한다.
2. **오버레이에는 "MCP라서 다른 것"만.** run-script 샌드박스 특성, MCP 응답 후처리 등.
3. **원장이 틀린 것 같으면 오버레이로 덮지 말고 사용자에게 보고한다.** 사용자가 원장 관리자에게 수정을 요청한다. 오버레이로 덮으면 그 오류가 원장에 영원히 남고, 다른 API 소비자(고객사 자체 개발·웹훅 연동)는 계속 틀린 문서를 본다.
4. **오버레이는 적을수록 좋다.** 각 항목에 삭제 조건을 반드시 적는다.
5. 의심스러우면 **라이브 스펙으로 검증**한다 — 인증 불필요:
   ```bash
   curl -s https://salesmap.kr/api/v2/openapi | python3 -m json.tool | less
   ```
   추측이나 probing보다 이게 빠르고 정확하다.

## 비공개 API는 문서에 넣지 않는다

MCP 내부적으로 미공개 엔드포인트를 쓰더라도 **`get-api-ref` 문서에는 공개된 것만 싣는다.**

이 문서는 AI가 `run-script`로 REST API를 직접 호출할 때 참고하는 자료다. 미공개 엔드포인트를 실으면 고객이 그걸 자체 연동에 쓰게 되고, 스펙이 바뀌면 그대로 깨진다.

> **선례 (2026-07-28)**: `salesmap-list-engagements`는 `POST /v3/object/activity`를 쓴다(`src/tools/extras.ts`의 `V3_ACTIVITY = true`). 한때 이 v3 스펙을 오버레이로 실었으나 제거했다. 개발팀 방침이 **"v3를 MCP 내부에서 쓰는 건 무방하나 공개는 곤란하며, v2를 근본적으로 개선해 v3보다 낫게 만들 예정"**이기 때문이다.
> **코드는 v3를 쓰되 문서에는 v2만 싣는다.** v2가 개선되면 원장이 갱신되고 우리는 그걸 그대로 받는다.
