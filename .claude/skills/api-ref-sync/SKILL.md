# API 레퍼런스 동기화

## 파일 구조

```
docs/internal/api-ref-upstream.md   원장 그대로.       ← 통째 교체만. 절대 부분 수정 금지
docs/internal/api-ref-overlay.md    우리(MCP) 지식.    ← 우리가 관리하는 유일한 파일
docs/internal/api-ref-merged.md     병합본.            ← 이 스킬의 산출물
src/tools/api-ref.ts                생성물.            ← 스크립트가 만듦. 직접 수정 금지
```

`salesmap-get-api-ref`가 내려주는 문서 = **원장 + 오버레이**.

## 병합은 LLM이 한다

원장은 **섹션 제목·문구·구조가 통째로 바뀐다.** 실측: 2026-06-30 → 07-28 갱신에서 547줄이 변했고, 표 컬럼 폭·용어("연결관계"→"연관관계")·섹션 신설이 뒤섞여 있었다.

그래서 기계적 문자열 앵커 매칭은 성립하지 않는다. **원장을 읽고, 오버레이의 의도를 이해해서, 적절한 자리에 녹여넣는 판단**이 필요하다. 스크립트는 이스케이프만 담당한다.

## 왜 이 구조인가

과거엔 원장을 복사해 직접 고치는 **포크** 방식이었다. 결과:

- 원장이 갱신돼도 반영이 안 돼 우리 문서가 stale해짐
- **2026-07-28 실측**: 파일 API에 대해 "레코드 첨부 불가 / 조회·삭제 API 없음"이라고 단언하고 있었으나 라이브 OpenAPI 확인 결과 **셋 다 존재**했다. `get-api-ref`를 읽은 AI가 고객에게 "그건 안 됩니다"라고 답하고 있었을 가능성이 높다
- 원장과 547줄 차이가 나서, 갱신할 때마다 "우리 수정"과 "원장 개선"을 손으로 가려내야 했다

오버레이 방식은 우리 것만 따로 관리하므로 원장을 통째로 받아도 안전하다.

***

## 절차

### 1. 원장 교체

사용자가 준 새 원장으로 `docs/internal/api-ref-upstream.md`를 **통째로 덮어쓴다.**

교체 전, 이전 원장과의 diff를 떠서 **무엇이 바뀌었는지 파악**한다. (5번 보고에 쓴다)

```bash
diff -u <이전_원장> <새_원장> | head -200
```

### 2. 오버레이 항목별로 판단

`docs/internal/api-ref-overlay.md`의 **각 항목마다** 다음을 순서대로 확인한다.

**(a) 삭제 조건이 충족됐는가?**
원장이 그 내용을 이미 담게 됐다면 **오버레이 항목을 삭제한다.** 가장 좋은 결말이다 — 유지보수 비용이 줄고, 원장이 우리보다 정확하다.

**(b) 아직 필요한가?**
필요하면 새 원장의 **어느 위치**에 넣을지 판단한다. 오버레이의 "어디에" 항목은 위치의 *성격*을 서술한 것이지 정확한 좌표가 아니다. 섹션 이름이 바뀌었어도 같은 성격의 자리를 찾는다.

**(c) 문구를 손봐야 하는가?**
원장의 용어가 바뀌었다면(예: "연결관계"→"연관관계") 오버레이 본문도 맞춰 고친다. 문서 전체가 일관돼야 한다.

### 3. 병합본 작성

원장을 기반으로 오버레이를 녹여 `docs/internal/api-ref-merged.md`를 만든다.

- **원장 내용은 임의로 지우지 않는다.** 우리가 v3를 쓴다고 해서 원장의 v2 스펙을 지우면 안 된다 — run-script로 직접 호출 가능하므로 여전히 유용하다. 덧붙이되 덜어내지 않는다
- 목차·상호참조가 있으면 함께 갱신한다
- 오버레이가 삽입된 자리가 문맥상 자연스러운지 읽어본다

### 4. 빌드 + 검증

```bash
node scripts/build-api-ref.mjs   # merged.md → api-ref.ts (왕복 이스케이프 검증 포함)
npx tsc --noEmit && npm run build
```

추가로 **반드시** 확인한다.

- [ ] 오버레이 각 항목이 병합본에 실제로 들어갔는가 (문자열 검색)
- [ ] 원장의 주요 신규 내용이 살아있는가 (diff에서 본 것들)
- [ ] 이전 병합본에 있던 내용이 이유 없이 사라지지 않았는가
  ```bash
  diff <(git show HEAD:docs/internal/api-ref-merged.md) docs/internal/api-ref-merged.md | head -100
  ```

> LLM 병합은 비결정적이다. **이 검증을 건너뛰지 말 것.**

### 5. 사용자에게 보고

- 원장에서 새로 들어온 주요 변경 (우리가 몰랐던 API·규칙)
- **삭제한 오버레이 항목** (원장이 흡수한 것 — 좋은 소식)
- **원장이 틀린 것으로 의심되는 것** ← 아래 참조
- 남은 오버레이 개수

## 원칙

1. **원장을 신뢰한다.** 세일즈맵 개발팀이 정기 갱신하는 공식 문서다. 우리 기억보다 우선한다.
2. **오버레이에는 "MCP라서 다른 것"만.** v3 마이그레이션, run-script 샌드박스 특성, MCP 응답 후처리 등.
3. **원장이 틀린 것 같으면 오버레이로 덮지 말고 사용자에게 보고한다.** 사용자가 원장 관리자에게 수정을 요청한다. 오버레이로 덮으면 그 오류가 원장에 영원히 남고, 다른 API 소비자(고객사 자체 개발·웹훅 연동)는 계속 틀린 문서를 본다.
4. **오버레이는 적을수록 좋다.**
5. 의심스러우면 **라이브 스펙으로 검증**한다 — 인증 불필요:
   ```bash
   curl -s https://salesmap.kr/api/v2/openapi | python3 -m json.tool | less
   ```
   추측이나 probing보다 이게 빠르고 정확하다.

## 현재 오버레이 (2건)

| # | 내용 | 삭제 조건 |
|---|---|---|
| 1 | run-script 응답 래퍼 벗김 경고 | MCP 고유 동작 — 사실상 영구 |
| 2 | 액티비티 v3 섹션 + v2 섹션 안내 + 목차·빠른찾기 병기 | **원장에 v3 액티비티가 반영되면 삭제** |

> 2번이 사라지면 오버레이는 1건이 된다. 원장 담당자에게 v3 반영을 요청해두면 유지보수 비용이 크게 준다.
