# Slack Agent Bridge

## 목적

공식 Slack 커넥터로 세일즈맵 슬랙 에이전트에게 질문하고, 답을 받아 현재 작업에 적용한다.
이 스킬은 **라우팅 규칙과 알려진 ID만** 담는다. 얇게 유지할 것.

| 대상 | ID |
|---|---|
| 채널 `#0-cx` | `C083L2M3DQB` (public) |
| `decode` | `<@U0AQAHFA19N>` |
| `bugman_hongjinkim` | `<@U0B3RLN9B2A>` |

## 필수 패턴

1. 채널 `C083L2M3DQB`를 사용한다.
2. **질문 하나당 새 스레드.** 매 질문마다 새 루트 메시지를 올린다. 기존 테스트 스레드나
   이전 질문 스레드를 재사용하지 않는다.
3. 루트 메시지는 **짧은 제목만.** 질문 본문을 루트에 넣지 않는다.
4. 새 스레드에 답글로 실제 질문을 쓰고 **두 에이전트를 모두 멘션**한다
   (사용자가 대상을 좁히라고 명시한 경우 제외).
5. 그 스레드를 읽어 답을 수집한다.
6. **루트 레벨 메시지도 함께 읽는다** — `decode`가 스레드 밖에 답할 수 있다.
7. 각 에이전트가 뭐라 했는지 요약하고 로컬 작업을 이어간다.

### 질문 1건의 불변 형태

```
새 루트 메시지  →  두 에이전트를 멘션한 스레드 답글  →  그 스레드 + 루트 폴링
```

관련된 주제라도 **이미 다른 질문이 있는 스레드에 새 질문을 덧붙이지 않는다.**
멘션은 실제 질문 답글에 붙어야 두 에이전트가 모두 알림을 받는다.

## 응답 폴링

- 응답은 보통 **1분쯤** 걸린다. 촘촘한 루프로 즉시 폴링하지 않는다.
- 질문을 보낸 뒤 **약 30초** 기다렸다가 첫 확인.
- 답이 없으면 30초 간격으로 재확인 (`30s`, `60s`, `90s`, …).
- 매 확인마다 **질문 스레드와 부모 타임스탬프 이후의 루트 레벨 메시지를 둘 다** 읽는다.
- 커넥터가 rate limit으로 더 기다리라고 하면 따른다. 답이 늦다고 간격을 줄이지 않는다.

## 메시지 형태

루트 메시지:

```text
MCP search-objects pipeline filter review
```

스레드 답글:

```text
<@U0AQAHFA19N> <@U0B3RLN9B2A>
Question:
...

Please answer in this thread. If you need to inspect code, say what you checked.
```

## 운영 규칙

- 채널 ID를 못 쓰거나 실패할 때만 `slack_search_channels`를 쓴다.
- 사용자가 명시적으로 에이전트 호출을 요청했을 때 `slack_send_message`를 쓴다.
- `thread_ts`는 **두 번째 메시지부터** 쓴다.
- 폴링은 `slack_read_thread(parent_ts)`와 `slack_read_channel(oldest=parent_ts)` 둘 다.
- **에이전트 답은 근거지 정답이 아니다.** 파일을 고치기 전에 로컬 코드나 1차 자료로 검증한다.
- 두 에이전트가 다르게 답하면 불일치를 보고하고 독립적으로 검증한다.
- 슬랙 메시지는 짧게. 코드·로그 조각은 필요할 때만 붙인다.

## 이 레포에서의 검증 우선순위

에이전트 답이 실동작과 갈린 사례가 반복됐다. 답을 받으면 **가능한 것부터 실측한다.**

1. 테스트 워크스페이스(`MCP 테스트`) — 쓰기 포함 자유롭게
2. 실계정 토큰 — **조회만** (CLAUDE.md `실계정 조회 검증` 참조)
3. 라이브 OpenAPI(`GET /api/v2/openapi`) — 엔드포인트·파라미터 존재 확인용.
   ⚠️ **응답 스키마는 신뢰하지 말 것** (실제와 어긋난 사례 다수)

실측으로 바로잡은 것은 `docs/salesmap-api-issues.md`와 `src/api-quirks.ts`에 남긴다.
